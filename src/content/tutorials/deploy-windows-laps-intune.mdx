## Scope and Assumptions

This guide plans a Windows LAPS pilot managed through Intune, with passwords backed up to Microsoft Entra ID. It is reviewed against documentation, not a report of an executed rollout. Example commands collect evidence; the policy steps change devices and require an approved pilot.

The decision is more than password rotation: the support team must be able to retrieve a current credential, use it through an approved recovery path and demonstrate that it rotates afterwards. Keep an existing recovery path until all three checks pass.

## Prerequisites

- Use a supported Windows release with Windows LAPS updates. Do not apply one Windows 11 KB number to Windows 10; verify the supported OS and update requirements in the [Windows LAPS overview](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-overview).
- Confirm Intune enrolment, licensing, policy permissions and reachable Microsoft endpoints.
- Establish whether the device is Entra joined or hybrid joined. Hybrid devices may back up to Entra ID **or** on-premises AD, not both. Entra registered devices are not supported for this scenario. [Join-state restrictions](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-overview#understand-device-join-state-restrictions).
- Inventory existing password managers and legacy LAPS policy. Do not allow two products to rotate the same account. Follow the [legacy LAPS migration guidance](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-scenarios-legacy) before removing an existing agent or recovery path.
- Identify the managed local account, its enabled state and the support process. A policy targeting an account does not by itself establish that the account is usable.

## Separate Policy Administration From Password Recovery

Creating a LAPS policy, enabling the tenant setting and reading a password are different permissions. Use the documented Intune role permissions for policy management and the Entra permissions for password recovery; do not assume all Intune administrators can read credentials. The [Intune LAPS overview](https://learn.microsoft.com/en-us/intune/device-security/laps/overview) documents these requirements.

Assign credential access narrowly. Use a delegated role such as Cloud Device Administrator, or an appropriate custom role, with the intended device scope. Check actual authorisation with a support operator account before a rollout. [Entra LAPS permissions and recovery](https://learn.microsoft.com/en-us/entra/identity/devices/howto-manage-local-admin-passwords).

Do not retrieve plaintext passwords merely to prove that escrow exists. Never place recovered passwords in screenshots, transcripts, CSV inventories or ordinary tickets.

## Enable the Tenant Capability

In Entra device settings, an authorised administrator enables the Windows LAPS tenant setting. This permits the backup capability; it does not configure every device. Record the existing value and obtain tenant-change approval before changing it.

Do not switch this setting off to recover one failed pilot. That could affect password backup for unrelated devices.

## Create a Narrow Intune Pilot

In **Endpoint security > Account protection**, create a Windows LAPS policy for the appropriate Windows platform. Use an **assigned pilot device group** first, rather than a dynamic rule that silently targets every managed device.

Decide the settings with the recovery owner:

| Setting | Pilot decision | Validation |
|---|---|---|
| Backup directory | Microsoft Entra ID for this workflow | Credential metadata appears for the correct device |
| Managed account | Built-in Administrator or an explicitly selected account | Account exists and enabled state matches the recovery design |
| Password length and complexity | Approved values supported by the OS | Generated credential meets policy without being copied into the change record |
| Age and post-authentication actions | Agreed rotation delay and logoff/reset behaviour | A controlled use produces the expected action at the expected time |
| Assignment | Small, representative device group | Only intended devices receive the profile |

Windows 11 24H2 and later offer additional automatic account-management capabilities; do not assume those exist on older clients. Check setting applicability in the [LAPS policy reference](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-management-policy-settings) and [Intune deployment guidance](https://learn.microsoft.com/en-us/intune/device-security/laps/deploy-policy).

For co-managed clients, review management authority and the effective policy on the device. **Account protection is an Intune policy area, not a co-management workload slider.** Check the supported [workloads](https://learn.microsoft.com/en-us/intune/configmgr/comanage/workloads) and eliminate overlapping LAPS configuration before widening scope.

## Validate Policy and Escrow Separately

Trigger an approved Windows or Intune sync and inspect per-setting policy status. A successful profile report is not sufficient evidence of password backup.

On the pilot device, run this read-only example from an authorised elevated PowerShell session:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-LAPS/Operational'
    StartTime = (Get-Date).AddDays(-1)
} -ErrorAction Stop |
    Select-Object TimeCreated, Id, LevelDisplayName, Message
```

For directory backup, event **10029** records success to Entra ID; **10018** is success to Windows Server AD. Event **10005** signals policy-processing failure: use its error and surrounding events to diagnose the cause. These are not interchangeable with local password-change events. [Microsoft LAPS event reference](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-management-event-log).

In the Intune or Entra device record, confirm the device identity and password backup timestamp. A missing pane can indicate permissions, platform applicability or absent backup, not just a display delay.

## Password Retrieval Is a Separate Recovery Action

Use the portal recovery workflow only when the approved support scenario needs a credential. If using PowerShell, Microsoft's cmdlet is `Get-LapsAADPassword` with `-DeviceIds`, and it requires Microsoft Graph dependencies and an authorised connection. It queries Entra; it is not a local LAPS health command. See the [cmdlet reference](https://learn.microsoft.com/en-us/powershell/module/laps/get-lapsaadpassword?view=windowsserver2025-ps) before choosing permissions or plaintext output.

Test one authorised recovery, then confirm the intended post-authentication action, subsequent backup timestamp and access audit. Record timestamps and outcomes, not secrets.

## Troubleshooting and Failure Modes

| Evidence | Next check | Avoid |
|---|---|---|
| Profile not applicable | OS support, join state and setting applicability | Assuming every hybrid device is unsupported |
| Profile applied but no backup | Backup directory, tenant setting, connectivity and LAPS events | Recreating device objects to refresh a portal |
| Password visible to one operator only | Entra role, scope and Intune permissions | Granting Global Administrator to fix a display issue |
| Rotation conflicts | All password managers and policy sources targeting that account | Two tools rotating the same credential |
| Credential works but does not rotate as expected | Post-authentication policy and its delay; event timeline | Concluding failure before the configured interval |

## Recovery and Rollback

1. Stop pilot expansion. Retain logs, assignment details and the current recovery owner.
2. If a policy setting is wrong, correct it within the pilot and verify effective device state and escrow again.
3. Before retiring LAPS management, establish and test the replacement credential-management and access process. Removing assignment does not restore a previous password.
4. Remove or revise only the pilot assignment through change control. Confirm resultant policy and account state; do not assume every setting reverts immediately.
5. If a credential was exposed, use the documented rotation action and verify a new backup. Deleting a device object or an imagined portal “delete password” control is not a substitute for rotation.
6. Confirm unrelated devices continue backing up successfully. Preserve recovery access until the replacement passes validation.
