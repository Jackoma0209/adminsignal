## What This Page Is

This is a research-based evaluation aid for administrators considering CrowdStrike Falcon Go. It is not an independent malware test, a product benchmark, a support-response test, a customer deployment report, or a claim that AdminSignal has operated the product in production.

Use it to prepare a vendor demonstration and a controlled pilot. Product packaging, support, retention, investigation features, update controls, and commercial terms must be confirmed against the current quotation and tenant documentation.

## Evidence Basis and Limitations

The notes use public CrowdStrike product material and technical documentation about the Falcon sensor, deployment tooling, policies, and sensor-update controls. Public documentation can show that a capability exists, but it does not prove that the capability is included in the exact Falcon Go package offered to an organisation.

Do not infer security efficacy, usability, support quality, or incident-response performance from this page. Those points require independent testing, contractual review, and evidence from a pilot that reflects the organisation's devices and operating model.

## Decision Frame

Start with the operating requirement rather than the product name:

- Which Windows, macOS, Linux, server, and virtual desktop platforms must be protected?
- Is the requirement prevention and basic alert handling, or does the team need threat hunting, detailed process investigation, managed response, or custom detections?
- Who will own alert triage, policy changes, exclusions, sensor deployment, sensor updates, and incident escalation?
- What Microsoft Defender capabilities are already licensed and operational?
- Which data residency, retention, integration, and support obligations apply?

A dedicated endpoint-protection platform can add value, but it also creates another control plane, sensor lifecycle, permission model, and incident workflow that must be owned.

## Deployment and Sensor Pilot

CrowdStrike publishes tooling and API documentation for installing and removing Falcon sensors and for working with sensor-update policies. A pilot should prove the complete lifecycle rather than only a successful installation.

Record evidence for:

1. Package acquisition and integrity checks.
2. Installation on each supported operating-system build.
3. Registration into the correct customer and host groups.
4. Proxy, firewall, VPN, and remote-user behaviour.
5. Policy assignment and precedence.
6. Sensor update, rollback, and uninstall workflows.
7. Coexistence or migration behaviour with Microsoft Defender and other security agents.
8. Helpdesk recovery when a device is offline, isolated, or unable to update.

Keep the pilot group small enough that a bad sensor or policy change cannot affect a business-critical fleet.

## Update Control Questions

CrowdStrike's technical documentation exposes sensor-update policies, builds, schedules, policy precedence, and uninstall-protection settings. Confirm what the purchased package and assigned roles allow administrators to do in the console.

Ask the vendor to demonstrate:

- How pilot, broad, and exception groups receive different sensor versions.
- How an update is paused, pinned, rolled back, or moved between policies.
- Which administrators can change policy precedence or uninstall protection.
- How update failures and devices on unsupported builds are reported.
- What recovery process applies if a sensor update disrupts startup, networking, or a line-of-business application.

## Investigation and Response Questions

Do not evaluate only whether an alert appears. Test what the team can do after the alert:

- Is the process tree and event context sufficient for the expected incident workflow?
- Can analysts search across affected hosts and retain evidence for the required period?
- Which containment, isolation, remote-response, and managed-response functions are included?
- Which actions require a higher package, additional service, or different role?
- What is the escalation path when internal staff cannot complete the investigation?

Use a harmless vendor-supported test method and document the expected alert, investigation fields, notification path, and closure evidence before the pilot begins.

## Exclusions and Change Control

Endpoint exclusions can reduce protection and should not become a permanent workaround for noisy applications. During the pilot, document:

- Who may request and approve an exclusion.
- The narrowest path, process, certificate, or indicator scope available.
- An expiry or review date.
- The evidence used to show the exclusion is still required.
- The rollback process if the exclusion creates unacceptable exposure.

## When Not to Choose This Operating Model

Pause or reject the purchase if the team cannot establish ownership for sensor updates, alert triage, incident escalation, exclusions, and policy recovery. A product can be technically capable while still being a poor fit for an organisation that lacks time, permissions, support coverage, or a tested incident process.

Also compare the proposed package with capabilities already licensed through Microsoft. Replacing one incomplete operating model with another is not an improvement.

## Evaluation Checklist

- [ ] Exact package name and current feature matrix obtained in writing.
- [ ] Supported operating systems and server workloads confirmed.
- [ ] Data location, retention, sub-processors, and contractual terms reviewed.
- [ ] Pilot, update, rollback, and uninstall workflows demonstrated.
- [ ] Investigation depth and response actions tested with safe evidence.
- [ ] Roles, least privilege, and approval boundaries documented.
- [ ] Exclusion governance and expiry process agreed.
- [ ] Microsoft Defender licensing and migration/coexistence plan compared.
- [ ] Support route, service hours, and escalation commitments confirmed.
- [ ] Exit plan and sensor removal process tested before broad deployment.
