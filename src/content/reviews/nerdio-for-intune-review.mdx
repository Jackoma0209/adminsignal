## What This Page Is

This page is a research-based evaluation aid for teams assessing Nerdio Manager alongside Azure Virtual Desktop, Windows 365, Intune, and existing Azure automation. It is not a product benchmark, a measured cost-saving study, a deployment case study, or a claim that AdminSignal has operated Nerdio in production.

Use it to structure architecture review, permission review, a vendor demonstration, and a controlled pilot. Confirm the current product name, edition, licensing unit, support scope, and feature packaging directly with Nerdio before making a purchasing decision.

## Evidence Basis and Limitations

Nerdio's current documentation describes Nerdio Manager for Enterprise as a deployment, management, and autoscaling platform for Azure Virtual Desktop and Windows 365. Its reference architecture documents an Azure-hosted application, Entra enterprise application permissions, Azure resource access, SQL, Key Vault, storage, Automation, Log Analytics, and Application Insights components.

Those documents establish the intended architecture and documented functions. They do not prove savings, usability, support quality, performance, or fit for a particular estate. Vendor cost models and savings statements are estimates and should not be treated as measured outcomes for your organisation.

## Define the Operational Problem

Record the current burden before evaluating another management layer:

- Number and type of AVD host pools and Windows 365 Cloud PCs.
- Frequency of image updates, host replacement, application changes, and scaling changes.
- Existing runbooks, Azure Automation, pipelines, monitoring, and service-desk procedures.
- Time spent on recurring administration and incident recovery.
- Current Azure compute and storage cost, including seasonal peaks.
- Skills and support coverage available to operate Azure, Intune, and AVD directly.

Without a baseline, it is difficult to distinguish a useful operating improvement from a polished demonstration.

## Architecture and Permissions Review

Nerdio's reference architecture states that the application is deployed into the customer's Azure environment and requires an Entra enterprise application plus permissions to the subscriptions or resource groups it manages. The deployment also creates or uses Azure platform components that carry cost and require monitoring.

Before deployment, document:

1. The resource group and subscription design.
2. The exact Entra and Microsoft Graph permissions requested.
3. Azure role assignments for the service principal.
4. Key Vault, SQL, storage, Automation, Log Analytics, and Application Insights ownership.
5. Network egress, private networking, firewall, DNS, and proxy requirements.
6. Update responsibility for the Nerdio application and supporting Azure resources.
7. Backup, disaster recovery, and break-glass access for the management layer.

Do not grant broad subscription or directory access without mapping each permission to a documented function and an accountable owner.

## Pilot Scope

Choose one non-critical host pool or a small Windows 365 group. Preserve the existing Microsoft-native procedure so the team can compare and recover.

The pilot should cover:

- Host creation, drain mode, session handling, scaling, and host removal.
- Image creation, versioning, update, deployment, and rollback.
- Application installation and failure recovery.
- Intune policy, compliance, and device-state visibility where included.
- Delegated helpdesk and engineering roles.
- Audit records for scripted actions and configuration changes.
- Service behaviour if Nerdio or a supporting Azure component is unavailable.
- Direct operation through Azure and Intune when the management layer cannot be used.

Capture screenshots, timestamps, logs, Azure cost data, and operator effort during the pilot. Do not rely on recollection or a vendor demonstration alone.

## Autoscale and Cost Claims

Autoscale can reduce unused compute when schedules and demand permit it, but savings depend on workload patterns, user behaviour, storage, reserved capacity, existing automation, and the configuration applied.

Before accepting a cost model:

- Compare it with at least four weeks of representative usage where possible.
- Separate Nerdio licensing and supporting Azure resource cost from compute savings.
- Include peak periods, patch windows, image maintenance, and disaster-recovery capacity.
- Record whether an existing scaling plan or Azure automation already provides similar control.
- Define a rollback threshold if availability, sign-in time, or support demand worsens.

Treat estimated savings as a hypothesis to validate, not a product outcome.

## Change Control and Recovery

A management layer can automate high-impact Azure actions. Define who may:

- Create, resize, stop, start, drain, or delete session hosts.
- Change autoscale rules and schedules.
- Publish images and applications.
- Run scripted actions.
- Change permissions, integrations, and update settings.

Use least privilege and require approval for broad or destructive actions. Keep the native Azure and Intune procedures documented until the team has proved it can recover from a failed automation, bad image, incorrect scale rule, or unavailable Nerdio application.

## Support and Exit Questions

Ask for written answers to:

- Which faults are supported by Nerdio and which remain Microsoft or customer responsibility?
- Which editions and add-ons include the features shown during evaluation?
- How are upgrades released, tested, delayed, rolled back, and supported?
- What configuration and audit data can be exported?
- What remains in Azure if licensing ends or the application is removed?
- How are open incidents handled during subscription or tenant changes?

## Evaluation Checklist

- [ ] Current edition, licensing metric, minimum term, and support scope confirmed.
- [ ] Architecture and supporting Azure resource costs documented.
- [ ] Entra, Graph, subscription, and resource-group permissions reviewed.
- [ ] Network and private-access requirements tested.
- [ ] One non-critical host pool selected for the pilot.
- [ ] Existing Azure/Intune runbooks retained as a fallback.
- [ ] Autoscale estimates compared with representative usage data.
- [ ] Image and application rollback tested.
- [ ] Delegated roles and change approval tested.
- [ ] Export, exit, and application-removal process documented.
