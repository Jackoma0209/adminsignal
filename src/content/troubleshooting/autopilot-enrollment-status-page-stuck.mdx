## Identify the failed phase, not just the percentage

Use this guide when Windows Autopilot's Enrollment Status Page (ESP) stalls or fails during device preparation, device setup or account setup. A 0% display is a symptom, not a diagnosis: app installation, policy tracking or authentication can still be relevant. Preserve the displayed stage, error text, time, device serial and deployment mode before retrying.

## Scope and assumptions

This guide covers classic Windows Autopilot deployment profiles on supported Windows 11 releases. Windows Autopilot device preparation has its own provisioning flow and does not use classic ESP; use the [Autopilot deployment comparison](/comparisons/autopilot-v1-vs-v2-2026) to identify the applicable model. Microsoft's [ESP configuration documentation](https://learn.microsoft.com/en-us/intune/device-enrollment/windows/setup-status-page) distinguishes these flows.

You need authorised access to the affected Intune device, deployment profile and app reports. Entra sign-in investigation requires the corresponding log-reading permission. Profile changes require appropriate Intune RBAC and scope. Diagnostic examples are illustrative and documentation-reviewed; no reproduced tenant failure is claimed.

## Collect the first evidence

Where log collection and diagnostics are enabled in the ESP profile, use View Diagnostics or **Ctrl+Shift+D** on supported Windows 11 devices. Availability depends on the deployment scenario and profile. See [Microsoft's Autopilot troubleshooting FAQ](https://learn.microsoft.com/en-us/autopilot/troubleshooting-faq). A missing diagnostic button is not proof of an enrolment failure.

If an authorised support session permits Shift+F10, collect diagnostics before resetting. The following Command Prompt example creates its destination first:

```cmd
if not exist C:\Temp mkdir C:\Temp
mdmdiagnosticstool.exe -area "Autopilot;DeviceEnrollment;DeviceProvisioning" -cab C:\Temp\AutopilotDiagnostics.cab
```

Keep the CAB in an approved support location. It can contain user, device and tenant identifiers. Use the portal's diagnostic collection when a local command prompt is unavailable; do not defeat restrictions to obtain one.

## Choose the next check from the evidence

| Evidence | Next check | What it does not prove |
|---|---|---|
| Wrong organisation branding or profile absent | Match the serial and tenant in Intune's Windows Autopilot device inventory; check profile assignment status | A local wipe will fix an inventory or assignment problem |
| Sign-in error at the failure time | Inspect the actual Entra sign-in record and Conditional Access result for the affected user/resource | Every enrolment failure is a Conditional Access block |
| Required application shown as failed or pending | Match app ID, assignment context, installer and detection result in Intune/IME logs | An app with an installer exit code of zero was detected successfully |
| Download or service connection errors | Check the approved provisioning network, proxy context and service endpoints | A failed ping proves HTTPS is blocked |
| Attestation-specific error in self-deploying or pre-provisioned mode | Check supported TPM/firmware and the documented attestation path | TPM clearing is a safe general repair |

This ordering prevents a common diagnostic loop: rebuilding the same device while the unchanged blocking app or tenant assignment fails again.

## Network, time and authentication

Use a known working, approved provisioning network without an interactive captive portal. Compare the failing device against another device on that network before changing security controls. A TCP test is only one layer of evidence:

```powershell
Test-NetConnection login.microsoftonline.com -Port 443
w32tm /query /status
```

`TcpTestSucceeded: True` does not validate TLS inspection, every required endpoint or authentication under the provisioning context. Review [Windows Autopilot network requirements](https://learn.microsoft.com/en-us/autopilot/requirements?tabs=networking). If the clock is wrong, correct it through the supported time configuration and document the difference; do not disable certificate checks.

For Conditional Access, correlate the failure time and application in sign-in logs. An enrolled/compliant-device requirement can conflict with the initial enrolment path, but the resolution must be scoped to the actual affected policy. Use What If/report-only evaluation on a proposed change and preserve existing protection while reviewing it. Do not broadly exclude a named location, all users or all cloud apps to make ESP pass.

## Apps and the ESP timeout

Inspect the configured ESP timeout and blocking-app list. The documented default is 60 minutes, but the assigned profile can differ. Increasing the timeout is reasonable only when the installation is progressing and measured pilot duration justifies it; it cannot repair an invalid detection rule.

Review `C:\ProgramData\Microsoft\IntuneManagementExtension\Logs` where IME is installed. Identify the exact app and correlate its installer exit code with detection, dependency, architecture and System/user context. Preserve the logs before another attempt. The [Win32 application troubleshooting guide](/troubleshooting/intune-win32-app-install-stuck-waiting) covers that branch in detail.

Limit blocking apps to the ones genuinely needed before the user reaches a usable, protected desktop. Pilot any change rather than allowing users to bypass all failures or removing security agents without an alternative control. Track whether the excluded app subsequently installs; passing ESP alone is not the success criterion.

## TPM-specific failures

TPM attestation is relevant to self-deploying and pre-provisioned scenarios; it is not a universal requirement of user-driven Entra-joined Autopilot. For an attestation error, collect the exact code and inspect TPM state:

```cmd
tpmtool getdeviceinformation
```

Check the documented hardware requirements and OEM firmware guidance. Do not switch TPM implementations, clear TPM or run an invented reset subcommand. Firmware and TPM changes can affect BitLocker and credentials, so confirm recovery access before an approved repair. A reimage does not resolve a persistent service, network or hardware incompatibility.

## Validation and recovery

After one scoped correction, repeat the affected deployment on the pilot. Record profile assignment, completion of each ESP phase, the blocking apps' detection results, expected policy state and user sign-in. Then verify Intune check-in and the security controls required for handover. Do not report success solely because the progress screen disappeared.

If the same error returns, retain both sets of diagnostics and undo the specific pilot policy change if it caused a regression. Resetting or reinstalling is a separate destructive action: preserve needed data and logs, establish recovery access and use an approved reset workflow only after diagnosing whether local state is the cause. Avoid deleting device registrations as a routine troubleshooting shortcut.
